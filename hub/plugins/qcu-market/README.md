## Review and consent

Browsing and search initiate no RPC. Opening/back navigation never installs or enables; leaving a pending review revokes its consent. Explicit status/preparation first checks Host version, protocol 4 and the exact catalog SHA256. Missing/stale Host stops before download and asks for a normal DSH restart; the market never restarts the app. Preparation downloads only a reviewed immutable release from `http://192.168.1.68:8080/plugins/<id-version-sha256>.tgz`, validates size/hash and obtains official inspect results. The in-memory five-minute receipt binds UUID, release key, catalog fingerprint, bytes and expiry. Returning or declining revokes review. No remote catalog, metadata hash or provenance grants installation permission.

Only **Confirm install (keep disabled)** uses the public `installBundle` with `enabled:false`, a new request ID and the reviewed registry. Before calling it, the flow rechecks Host, bytes, receipt, inventory and inspect result. Changed catalog, expiry, profile state, source/hash or registry invalidates consent. Each card has independent state; preparation, review, mutations and unresolved outcomes block operations on other cards. No automatic retry or compatibility/build exemption is added.

Installation success requires the exact bundle/version and disabled inventory plus official stage `enable`. Installation consent is separate from activation. The snapshot binds the catalog, release, transport, expiry and all exposed bundle/row inventory fields. Each mutation checks matching Host and unchanged inventory. After bundle enable, refreshed inventory decides whether the sole row is already active or needs its exact entryId enabled; an active row is never enabled twice. Wrong/multiple rows or overrides are refused, with no inferred component selection. Failed, overridden, unknown or restart-required outcomes stop the sequence. Leaving, unmounting or connection reset revokes authority for any later mutation; an already sent mutation is not cancelled. Its actual result/partial inventory stays visible. Lost replies retain a cross-entry lock and allow only read-only reconciliation; remaining activation requires fresh consent, without repeating uncertain enables. Cancellation uses official `cancelInstall`; not-running, too-late, lost replies and unknown outcomes never imply success/cancellation and block repeat installs. `waitForInstall` reconciles the original request.
