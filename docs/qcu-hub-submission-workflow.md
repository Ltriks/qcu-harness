# QCU Hub 投稿、审核与发布计划

2026-10-20。状态：首个本机投稿／审核／发布候选 MVP 已实现并通过合成材料测试与真实 Chromium 验收，见 [MVP 说明](qcu-hub-submissions-mvp.md)。尚未部署或真实发布；公开快照切换、撤回、市场关联发行和部门试用仍待后续完成。下述完整发布流程是后续契约，不代表本机候选已经上线。

## 当前已有与缺口

- P10 已有开发者交付模板、schema 1 submission、独立成员清单、离线 Python 标准库检查器、管理员人工审阅规范和合成测试。复用 scripts/qcu-check-submission.py 与 templates/qcu-submission/。
- 当前 hub/release/serve-hub.py 只读 GET/HEAD，POST 返回405。公开下载资源必须是 manifest allowlist 中的固定快照；它没有投稿、登录、审批队列或发布权限。
- 现有 P10 静态通过始终要求人审；不等于安装、启用、教师通过或允许发布。
- 市场当前审核目录随插件固定，Host 逐条核验固定版本、大小和 SHA256。Hub 更新目录本身不会授予现有市场新产品的安装权限。

## 首版用户流程

1. 同事按 devkit 提交一个 handoff：submission.json、最终 TGZ、源码和构建说明、许可与来源、独立成员清单、依赖锁证据、分阶段测试证据。网页选择本地文件；模板产品与草案不可冒充完成产品。
2. 系统接收至独立隔离区，分配投稿编号，冻结原字节并复算大小与 SHA256。只解析材料，不执行插件、安装脚本、构建命令或访问提交者 URL。
3. 调用既有 P10 检查器，页面展示错误、不支持项、人工复核项。失败不能进入批准；静态通过展示“待人工审核”，不能显示“安全/可安装”。
4. 审核者检查源码、许可、权限、数据影响、原生安装与教师业务证据，填写通过或退回理由。未测明确保留。
5. 审核通过后仍单独查看发布预览：产品身份、固定版本、来源、TGZ、大小、SHA256、材料摘要、审核人与证据、目录变化和旧版本保留情况。
6. 明确确认发布后产生新的不可变发行快照。发布后从实际下载入口核验长度、SHA256及白名单路由；失败保留记录并恢复上一完整快照，不能就地改旧包。
7. 同事看到投稿进度与退回理由；老师只看到当前已发布产品、历史固定版本及实际兼容边界。撤回仅停止推荐/新增安装来源，不远程删除已安装插件或成果。

## 状态与批准绑定

推荐业务状态为 draft → submitted → checking → needs-changes / in-review → approved → release-prepared → published；发布失败单独 recorded，withdrawn 为后续维护事件。状态更新由服务器校验，不能接受客户端直接写 approved/published。

静态检查结果、人工决定、发布预览都绑定同一冻结投稿版本和材料摘要。任意包/源码/权限/证据材料改变，必须新建修订并重新检查、审核，旧批准不能沿用。相同产品版本相同字节可识别重复投稿；相同产品版本不同字节拒绝覆盖，要求新版本。重复发布请求不得产生重复副作用。

审核和发布是不同决定。首版可以同一维护者承担两种角色，但要有两个明确动作与各自记录，不能自动批准自己的表单。

## 最小实现范围与部署边界

- 先做本机管理员工作流和浏览器可验证原型，再开放经确认的部门投稿入口。开发仅绑定127.0.0.1，不给现有192.168.1.68:8080增加匿名写入路由。
- 公开下载服务保持只读；隔离投稿、检查报告、审核日志与发布目录物理分开，不能被下载目录遍历到。
- 接收体积/成员数/展开量有上限；拒绝路径穿越、符号/硬链接及危险归档格式。安全落盘与P10检查是两步，不能先随意解压再检查。
- 使用现有 Python/JS 与本地文件状态，首版不引入对象存储、构建农场或大数据库。检查任务和发布记录持久化，中断后可核对原任务，不自动执行未知操作。
- 投稿与管理必须有身份与权限边界；管理变更防跨站请求，不把令牌写URL/公开日志。正式内网开放前需确认组织已有身份/传输入口；本文件不授予新账号、凭据、公开网络或权限扩大。
- 不在管理网页执行待审包、不代填教师 API Key，不复制凭据，不让“上传成功”触发 DSH 安装/启用。安装和启用仍由老师确认。
- 页面只展示真实可操作状态；技术报告折叠，投稿者可看到下一步和需要补齐的具体材料。

## 与 DSH 市场发行的连接

第一版沿用固定审核目录：发布准备阶段同时产生 Hub 候选快照和市场目录变更提案。维护者验证并构建新市场候选，确认该 Host 确实允许新增的精确产品版本，然后作为关联发行发布；旧市场对不在其白名单的包继续拒绝。

因此，“Hub已发布”和“当前这台DSH市场已可安装”分别展示，不能承诺现有客户端即时出现新产品。服务端动态可信目录是独立后续设计，需要明确验证信任根、签名/撤回/有效期及用户确认，首版不通过跳过校验实现。

## 开发顺序与退出条件

| 轮次 | 交付 | 验收条件 |
| --- | --- | --- |
| 当前：工作台可靠性与完整修订 | 初始连接、状态检查、完整编辑及离线回归 | 浏览修订不依赖模型就绪；错误状态准确；应用/放弃/保存确认不串任务 |
| 已完成本机 MVP：投稿、审核与候选准备 | 隔离上传、P10、状态页、退回/批准、摘要绑定预览、不可变本机候选及附件下载 | 合成合法/恶意/缺材料/重复/变更、未授权拒绝、恢复与浏览器流程通过；不提供真实发布动作 |
| 后续：真实发布闭环 | 不可变公开快照、目录关联发行、实际公开下载核验、撤回记录 | 旧包原字节保留；发布中断不暴露半成品；拒绝覆盖与重复发布；新旧市场能力区别准确 |
| 随后：部门试用 | 一名同事真实投稿、维护者审核发布、老师安装验收 | 指定无个人信息测试包完整走通，拒绝分支也有证据，再扩大到3–5位老师 |

本轮只完成本机准备链路，不宣称 Hub 已部署、候选已发布或老师可安装。后续按会话授权范围推进并分别实测；真实部署及权限变化仍须符合既有授权边界，不以排期替代验收。
