# QCU dedicated-launch policy lifetime

This is a decision and operations reference for the downstream thin-native candidate dated 2026-10-04, not a released upstream feature or a production approval. All policy guarantees below require the trusted launcher to install policy before any profile entry and retain its owner for the Host process lifetime. The candidate implements that selection through an independent fixed QCU Office entry and separate data roots; no mutable mode record is used. The [upgrade guide](../upstream/source/docs/upgrade-guide/v0.2.0-rc.2/qcu-dedicated-launch/guide.md) describes the candidate-specific change. [VALIDATION.md](VALIDATION.md) owns recorded acceptance results; [MAINTENANCE.md](MAINTENANCE.md) owns broader bundle/native maintenance.

## Failure being addressed

The earlier candidate installed tool and attachment restrictions as effects of the QCU business plugin. Actual Cordis unload tests showed ordinary tools rejected and attachment HTTP requests returning 403 while loaded, then ordinary tools executing and attachment requests reaching the next handler after explicit unload. Negative or missing native teardown acknowledgment did not preserve those effects. The original 28 disabled profile rows also belonged to the business bundle's patch, so removing its selection/configuration removed those restrictions from subsequent composition. A closed native panel therefore did not imply a restricted profile.

The fix separates business availability from policy lifetime. Business removal remains a supported lifecycle event inside a dedicated process; it is never permission to turn that process into an unrestricted profile.

## Fixed entry, data roots, and policy lifetime

The candidate's [Desktop package metadata](../upstream/source/apps/desktop/package.json) selects `lib/qcu-main.js`. That [fixed entry](../upstream/source/apps/desktop/src/qcu-main.ts) configures QCU before dynamically importing shared Desktop main code. Only after every configuration operation succeeds does it add that exact Electron App identity to a private process-local WeakSet. Shared main reads `isQcuOfficeLaunch(app)`; no separate record setter, release, or reset API is exposed. The `qcu-dedicated` switch is diagnostic only: a bare flag or inherited environment cannot authorize dedicated mode, and removing the diagnostic switch cannot clear a successful setup. Launching ordinary `lib/main.js` directly does not call the QCU identity/data-root configurator and leaves the App unmarked.

[Entry configuration](../upstream/source/apps/desktop/src/qcu-office-entry.ts) sets the app name to `QCU Office` before Electron becomes ready. Beneath the platform's existing application-data directory, it selects `qcu-office` as application data, `qcu-office/electron` as user data, `qcu-office/session-data` as browser session data, and `qcu-office/home` as `DSH_HOME`. It replaces inherited `user-data-dir`, `DSH_DESKTOP_USER_DATA_DIR`, and `DSH_HOME` selections. Directory-setup failure stops before shared main imports; there is no ordinary-data fallback or automatic copy/migration of an existing profile.

The QCU root and its direct directories must be real directories, not symlinks. New directories use mode `0700`; POSIX checks require existing directories to belong to the current user and have no group/other permission bits. Existing permissions are never modified to make a path pass. Invalid, non-directory, symlinked, or publicly accessible paths fail closed. Windows native ACL isolation still requires platform qualification. Generic development-launcher logs can show home/user-data inputs before this wrapper replaces them; those lines are not evidence of effective QCU paths.

The modified shared Electron main reads the process-local App record once. `HostProcess` carries that immutable choice to every child it starts as private `DSH_QCU_DEDICATED=1`, after deleting any inherited value. `DSH_QCU_PRIVATE_IPC` continues to advertise the native handshake independently; it does not select policy. Neither setting is a credential, and the process-local record is not a persistent mode file.

Desktop Host evaluates [qcuDedicatedLaunch](../upstream/source/apps/desktop-host/src/qcu-launch.ts) before mounting profile entries. Without dedicated selection, a resolved or skipped formal `qcu-thesis-workbench` bundle causes startup rejection. With dedicated selection, the policy is installed even when the business bundle is missing, disabled, or removed. An ordinary profile with no selected/skipped formal QCU bundle remains ordinary.

The trusted, code-only `runProfile.prepareRoot` callback installs [qcu-policy.ts](../upstream/source/apps/desktop-host/src/qcu-policy.ts) before any configuration-tree entry mounts. It is not a YAML field or an unloadable policy row. The fixed configuration is exactly `{ version: 1 }`; there is no mutable allowlist or production disposer.

The policy uses an independent Cordis `Context` sharing the Host event bus. Its listeners and official `ToolRuntime` guard effects belong to that independent owner, which is retained until process exit. They do not belong to the business fiber, tools provider fiber, Loader tree, or Host-root effect scope. Service replacement rebinds the official service while retained runtime references keep their guards.

The supported candidate route is its fixed QCU Office entry plus the matching patched Desktop Host, with business composition supplied through official profiles and bundles. Every cold launch of that entry selects the same dedicated mode even after business removal. Switching to ordinary DSH means terminating QCU Office and using the separate ordinary application entry; QCU Office never automatically falls back to it.

A pure official CLI launch of the standalone bundle does not invoke this policy installer. An untouched official Electron shell does not acquire it by installing the bundle. `--qcu-dedicated` is not a new public `dsh` CLI option. Synthetic CLI fixtures that explicitly supply the trusted preparation callback verify that callback; they do not make ordinary CLI deployment protected.

Any mode change requires terminating the whole Electron application and its Host. Reloading a plugin, editing profile rows, replacing a Host under the same launcher, or retrying native availability cannot change the current process's choice. Restarting QCU Office remains dedicated. The launcher and policy code must be upgraded together.

The dedicated candidate disables the ordinary Desktop update coordinator's packaged-source path and rejects any configured ordinary mandatory-release policy. There is no qualified QCU installer, release feed, or automatic application-upgrade compatibility guarantee here. Reusing the ordinary application's updater could replace the fixed entry, so a future QCU release pipeline needs separate verification.

## Launcher-owned disabled entries

[qcu-profile-policy.ts](../upstream/source/apps/desktop-host/src/qcu-profile-policy.ts) owns the original 28 root-entry disable rows independently of the business bundle. The dedicated Host passes fresh copies through `runProfile.launchPatches`; `ProfileContext` retains those separately from mutable bundle, profile, home, and invocation layers. [readProfilePatches](../upstream/source/packages/boot/app-boot/src/profile-context.ts) appends cloned launcher restrictions last, after those layers and the telemetry patch, on startup and each reconciliation. A user patch containing `disabled: false` therefore cannot re-enable a restricted row, and business metadata removal cannot discard the launcher rows.

Each launcher restriction must contain exactly a literal root-entry `id` and `disabled: true`. IDs must be unique, use the accepted literal-ID characters, and exist in the composed root before restrictions are appended. Wildcards, extra fields, false values, malformed rows/containers, duplicates, and missing targets are rejected before Loader reconciliation. Startup stops on rejection; a rejected reload leaves the previous running tree in place. A profile without `launchPatches` keeps ordinary composition behavior.

These 28 target IDs belong to the supported standard Web/Desktop profile. A changed upstream or custom profile missing one is incompatible with this fixed launch until its restrictions are deliberately reviewed; warning and skipping would weaken the selected application. The source file owns the exact list, while a parity test checks it against the original business bundle. This configuration restriction and the detached runtime guard are complementary: neither depends on the QCU business plugin remaining loaded. Direct mutation by arbitrary trusted Node code remains outside the guarantee.

## Admission rules and failure behavior

- While the official tools service is guarded and the Host is active, only `qcu_thesis_open` and `qcu_thesis_check` are admitted through `ToolRuntime`. Prefix matches and unrelated tools are denied. Existing business checks remain additional restrictions.
- Attachment upload/file routes on the Host connection are rejected before body transfer. Structured attachment content is rejected at both agent-step and model-stream entry. Ordinary text mentioning a filename is still text. QCU's isolated local document task remains a separate path; this policy does not send document contents to the model.
- Until a supported tools service is bound, HTTP ingress returns 503, tool execution is denied, agent steps are rejected, and model streaming fails. This includes tools-service removal before a replacement becomes ready.
- Host-root disposal closes admission synchronously and permanently for that Host process. Its retained listeners and captured official runtime guards continue to deny after disposal. Reusing or remounting that root cannot reopen the policy.
- A tools guard-binding failure terminates the dedicated Host synchronously. A logged error, rejected startup promise, or delayed shutdown alone would permit queued work to resume; none is the production fallback.
- These are admission rules, not cancellation of already accepted work. Native view teardown acknowledgment and Python shutdown remain separate obligations. The policy offers no release operation that waits for their success and then drops restrictions.

## Alternatives rejected

| Alternative | Reason it does not meet this candidate's requirement |
| --- | --- |
| Keep policy in the business plugin | Unload removes the effects whose continued presence is required |
| Add another ordinary policy plugin row | The Loader can disable, remove, or reload that row; a profile edit would still control policy lifetime |
| Attach all policy effects to Host root | Root disposal removes ordinary root effects; late callbacks and captured tool runtimes still need denial |
| Require native acknowledgment before removing business policy | Cordis teardown does not make a failing disposer a transactional veto; the earlier test failure remains possible |
| Infer dedicated mode from current business presence | Business removal would silently change security behavior, and absent/disabled startup could begin unrestricted |
| Treat the temporary command-line flag as durable selection | A later application launch can omit it; business absence then no longer distinguishes a formerly dedicated installation from an ordinary one |
| Accept a bare flag as proof of fixed-entry setup | Ordinary main can receive that flag without QCU data-root configuration; only successful setup of the exact App identity marks this process |
| Keep the 28 disabled rows only in the business bundle | Removing bundle metadata drops that composition layer; launcher-owned restrictions must be applied again after mutable layers |
| Reuse the private native-IPC capability marker | The shell can advertise native support for an ordinary Host; transport availability and dedicated policy are different facts |
| Allow live switching to ordinary mode | Safe switching would require a separately designed whole-process quiescence transaction; restarting the application supplies the current explicit transition |

## Supported providers and persistent Node limits

The service-binding guarantee covers one shared service with the exact official `ToolRuntime` prototype and standard class-plugin lifecycle, including initial activation, restart, and replacement through Cordis. It is not a general provider framework. Isolated tools scopes, direct construction on an already-active root, and custom service implementations are unsupported; binding failure terminates the process rather than weakening policy.

Trusted Node code can retain references, mutate shared objects, register earlier listeners, invoke native capabilities directly, or execute inside its own provider initialization before activation. This design does not isolate arbitrary same-process Node code, Python, or same-privilege local processes. Tool-name admission also assumes trusted code owns the two permitted implementations. A new untrusted-provider requirement needs a different execution/security design, not another policy row.

The subsequent [parent-lifetime fix](HOST-LIFECYCLE.md) couples new Host-managed Python children to a private stdin pipe. It is independent of policy lifetime and preserves conservative refusal of unknown or previously orphaned live services. A live recorded PID must never be treated as stale or killed solely because it appears in an old record. Runtime and platform limits remain explicit.

## Development, debugging, and upgrades

1. Develop in a separate checkout and synthetic home/profile. Test the fixed entry with an isolated substitute for the platform application-data directory; do not run it against a user's data as a unit-test shortcut. Keep user documents, model credentials, the stable r5 installation, and the user's existing profile outside the test run. Preserve the baseline, patch, external bundle, lockfile, and resource hashes independently.
2. Treat launch selection, pre-entry installation, policy lifetime, and business/native ownership as separate checkpoints. An absent QCU panel may mean business/native unavailability while policy correctly remains active. Do not diagnose it by enabling unrelated tools or sending attachments through the main model conversation.
3. Rebuild the modified launcher and Host together after source changes. Use the migration guide's test owners and the executed commands recorded in `VALIDATION.md`; maintain exact Node/DSH dependency identity between the bundle and checkout. A successful compile cannot replace lifecycle observations.
4. For a startup refusal, check that `lib/qcu-main.js` completed QCU data-root setup and marked the App, the standard profile still contains every restricted root ID, launcher patches remain valid, selected/skipped bundle metadata is correct, and policy version/tools binding are valid. Do not work around refusal with a bare dedicated flag, native-IPC marker, skipped restriction, or unprotected CLI launch. A rejected reload retains the old tree; a policy-failure Host exit requires diagnosis and a whole-application restart.
5. For a DSH upgrade, recheck the fixed entry's process-local identity, `runProfile` preparation order, last-applied `launchPatches` on every reconciliation, all 28 target IDs, synchronous service notifications, official `ToolRuntime.guard` ownership, Cordis disposal/restart ordering, and attachment/model entry points. Re-run real lifecycle and standard-Web restriction tests before accepting the patch. Retain native teardown and Python cleanup checks independently.
6. After the synthetic checks pass, obtain the separately authorized target-platform verification before deployment. Do not overwrite running assets or infer automatic migration, downgrade compatibility, rollback, or OS sandboxing from this policy fix.
